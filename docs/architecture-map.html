目标架构一次任务怎么走插件如何装卸实际源码关系

目标架构：产品运行时带插件，而不是插件写进核心

下面是待实现的目标，不是完成声明。编排、蜂群、SoL-Pi 分别是插件；技能、记忆、提示词也不归蜂群独占。

桌面入口聊天、会话选择、工作区、审批、状态展示只调用公开服务，不自己再造一套执行循环。
命令行入口交互、参数、输出与取消与桌面使用同一个运行时和同一套插件契约。
启动装配读取可信配置、发现插件、检查依赖、启动插件树新增插件改配置或插件清单，不修改循环代码。
通过公开服务调用 ↓
小核心 / 插件宿主
共享词汇与服务契约 · 服务注册与依赖检查 · 事件分发 · 插件作用域与资源撤销
安全底线仍由核心掌握：可信根、权限上限、审批判定；插件不能给自己放权。
声明需要的服务 / 提供服务 / 订阅事件 ↕
执行循环插件一次任务的步骤、模型请求、工具批次、取消与继续只依赖服务契约，不按名字认识编排或蜂群。
模型插件提供统一模型调用；连接兼容接口、离线模型替身等凭据与模型设置由产品管理，不由能力插件私自覆盖。
会话插件消息日志、恢复、事件追加、状态投影对话日志仍是对话唯一事实源；投影可以重建。
工具插件工具目录、参数校验、执行分发、结果回传文件、命令、后台作业按各自插件注册；执行仍过核心权限门。
提示词 / 技能 / 记忆插件提示词分段、技能目录、显式记忆、任务状态按服务与事件协作，不强行合成一个蜂群插件。
外部连接器插件外部工具发现、协议桥接、连接管理外部返回内容按不可信数据处理，不能改变权限。
编排插件理解任务 → 匹配技能 / 提示词 → 组装本步输入接入：进入步骤之前；可返回组装后的消息或明确拒绝。
蜂群插件选择方法 → 周期记录 → 验证 / 评审 → 回灌与演化接入：任务准备、工具执行前后、任务验收；库与成绩属于插件存储。
SoL-Pi 能力插件先承接已采用的工具结果投影与按需召回接入：构建模型上下文与召回工具；不是把召回当作整个 SoL-Pi 已完成。
三类事件
会话事实：追加后可恢复　|　执行过程：进入步骤、请求、停止、继续、验收　|　能力调用：工具执行前后、文件访问、遥测

一次真实任务怎么走（目标流程）

顺序负责者交出去什么 / 怎么处理失败
1入口 → 执行循环原始请求、工作区、权限档与取消信号；不由仓库配置自动提权。
2编排 → 技能 / 提示词服务任务目标、匹配结果和组装后的输入；缺事实就记录缺失，不编造。
3蜂群 → 方法库候选方法、选择结果和本轮记录；没有适用方法必须显式说明。
4会话 / 提示词 / SoL-Pi → 模型从日志读取事实、组合提示、投影过大的结果；原始结果保留，可按需召回。
5模型 → 工具服务 → 核心权限门工具请求先校验参数与权限，再检查插件约束；任何拒绝均停止该调用，不绕过。
6工具执行 → 会话 / 蜂群结果与实际写入证据；日志保留事实，蜂群记消耗与验证，不只相信口头声明。
7验收 → 蜂群回灌 → 入口展示产物、验证证据、评审结果；欠验证就不宣称完成，真实结果再进入成绩。

插件装卸与存储边界

启动读取可信插件清单 → 检查依赖 → 按依赖启动 → 注册服务与事件缺服务、依赖成环、重复注册或启动失败必须明确报错，撤销已经注册的资源。
运行与停止每个插件拥有自己的作用域；监听、作业、连接都登记撤销动作停止时取消正在执行的工作，按依赖逆序卸载；卸载不能留下旧监听或重复工具。
存储会话插件保管对话事实；蜂群保管方法与成绩；记忆插件保管显式记忆不复制同一份对话真相。迁移需有格式版本与恢复验证，卸载不等于删数据。
完整验收，不只看“能加载”
新增和替换插件不改核心；移除可选插件能正常运行；缺必需服务明确失败；卸载后无残留；两种入口走同一边界；插件不能越权；既有任务恢复与产物验收仍通过。

二、实测发现一个环 —— 架构文档的立论之一已经过期

架构文档 §3.4 ① 写着「36 个文件的内部 import 图无环」，并说「这一条决定性地回答了是否在错误的地基上建造」。
现在有环了。

taskspec.ts:15       import { classifyIntent } from "./intent-classifier.ts"
intent-classifier.ts:24 import { extractSignals } from "./taskspec.ts"
intent-classifier.ts:25 import type { TaskIntent } from "./taskspec.ts"
types.ts:13           import type { TaskIntent } from "./taskspec.ts"　← 词汇表反过来依赖了要变成插件的文件

根因：TaskIntent 这五个词（建 / 修 / 查 / 验 / 运维）是整套蜂群的词汇（基因的意图、周期的意图、选择策略都在用它），却住在 taskspec.ts 里 —— 而那个文件在 D173 里是要变成插件的。

修法就是这个文档自己写过的配方（§3.4 ③：共享词汇进 types.ts，行为留在外面）。两处搬家：

  1. TaskIntent 搬进 types.ts　→　types 不再依赖 taskspec，intent-classifier 的类型那一半也解掉
  2. extractSignals 搬进一个独立小模块　→　taskspec.ts:122 和 intent-classifier.ts:53 都指它，环消失

注意第二条是必要的：extractSignals 定义在 taskspec.ts:71，但它同时被 taskspec 自己（生成 signals）和 intent-classifier（分类前先切词）使用 —— 所以只搬类型不够，行为也得搬出来。

脚本扫出的环：taskspec -> intent-classifier -> taskspec

七、要接入的三个内核：挂上接缝，不是写进核心

内核接入方式现在的状态（实测）
编排（TaskSpec）上游的编排插件就是挂在「进入这一步」的钩子上，必要时改写要发给模型的消息已落地，但是核心模块：taskspec · intent-classifier · taskspec-prompt · constraints。
而且它现在是那个环的一半。
蜂群纪律层基因库 + RSI 闭环；PDRI 是骨架不是核心。它是一个插件，不是核心的多 Agent 框架已接进桌面入口（提交 a7caa5a），但是作为核心模块接的。整族 17 个模块、约 220 KB。
SoL-Pi先接一个只读能力，走现有 Schema、Policy 和批准；不让它成为独立 agent只落了召回一半：obs-recall。而且实测它一次都没触发过（D168 量 0/230），D169 已把门槛降到一页。

八、明确不做（两条不许被插件化动摇）

ADR-0001：会话日志是对话的唯一事实源。插件可以有自己存储（任务状态、周期账本），但对话事实只在会话日志里。

独立运行：接缝层优先用标准库，不依赖 DSH 宿主或 Cordis 运行时。不能把历史的“零生产依赖”当成现状：本轮已发现产品有 YAML 与压缩包读取依赖。
