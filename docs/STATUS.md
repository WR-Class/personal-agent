**权限架构的关键修正（D22/D23/D24，本批无代码）**：用户反馈"全都要弹窗很麻烦、但边界必须有"，并指出我提的"只读白名单"形态不对。调研了**本项目正在运行的 DSH 自身**（四个权限包的 README，直接从 `app.asar` 读取）、**gemini-cli**（策略引擎源码，深度）、**codex**（审批+沙箱源码，深度）、**crush** 与 **claude-code**（类型定义/源码）。三批结论递进：

1. **D22 根因**：我把"沙箱"和"审批"当成一个机制。它们是两个正交旋钮，且对用户应呈现为**具名档位**（`custom` 可见但不可选）。
2. **D23 内核**：实现应采用**单一优先级规则表 + tier 前缀**（Admin > User > Workspace > Extension > Default **不可倒置**，`priority` 上限 999 防 tier 溢出）。这样"降低打扰"的每一项功能都只是又一条规则，**结构上只能"胜过"某条规则、无法绕开排序**——比"两套机制各自守规矩"更有保证力。
3. **D24 修正重心（最重要）**：**Codex 的降打扰靠沙箱，不靠审批**——受限沙箱下普通命令**静默放行**，审批只是窄的例外通道。**而 Windows 恰是边界最弱的平台**：上游原版 Windows **没有沙箱**，其非升权后端**只能约束写**（读不受限），且**在没有边界时反而强制弹窗**补偿。因此在 Windows 上"审批"不可能成为主要边界。**本项目的诚实定位**：边界 = 路径收敛 + 写预算 + `WritableRoot` 式只读保护 + 子进程环境白名单 + 有界输出 + 审计 + 窄化授权，**而不是隔离**；SAFETY 必须**逐条列出这些不是隔离**。

4. **D25 第三条轴（最重要的一条修正）**：**降打扰不能只靠"调沙箱/调审批"，还要靠"让能力不存在"**——四个独立项目收敛于此（Letta `--tools ""` 原文"把工具从上下文里整个移除"、OpenClaw 只读会话不提供写工具、TrustClaw 按缺席拒绝、nanobot 越界路径不可达）。**疲劳 ∝ 决策数 ∝ 动作空间大小**，所以**缩小动作空间是唯一结构性的降打扰手段**，而不是让提示更聪明。**这修正了 D24 的结论**（D24 说"无沙箱⇒审批为主"，方向对但不完整）。另外两项独立证据：**goose 发布过 macOS 沙箱又把沙箱删了**（原文"has been removed … **not** sandboxed at the OS level"，转回 `GOOSE_MODE` 审批档——已在源码逐字核对，说明**持久价值在逻辑层而非隔离层**）；**qwen-code 让"总是允许"无法击穿自己的分类器**（危险 allow 规则被暂存而非安装，已在源码逐字核对）。

**本批落地顺序（三轴替代两轴，全部无需 shell、可立即实现并测试）**：①**能力存在性**（会话级工具集合——缺席即无需审批）＋**仓库外记忆化**＋**各轴独立** → ②**授权绑定内容哈希 + 执行前复验 + 漂移即拒**（与已有写入账本"执行前算账"同构）→ ③规则表内核（D23）→ ④影子快照/选择性还原（**可部分弥补"无沙箱＝无回滚"，候选**）→ ⑤命令执行。

**① 能力存在性已完成（本片，已测）**：`ToolRegistry` 增加可选 `available` 集合与 `has()`；**缺席在两个方向同时强制**——`definitions()` 不向模型暴露该工具，`execute()` 按名字拒绝。**只从提示词里藏起来、却仍能被调用，那是"伪装成缺席的拒绝"**，而这个边界之所以廉价，正因为它**只在两处一致时才成立**。拒绝文案刻意与普通失败区分：**"this tool is not available in this session; it is a policy boundary, not a transient failure"**——让模型知道这是本会话的**常驻属性**，不要重试或找绕路（依据：nanobot 的边界错误文案、opencode 的 `CorrectedError` 把原因回给模型）。改动仅 `src/tools.ts`（`available` + `has()` + `definitions()` 过滤 + `execute()` 前置拒绝 + 未注册项校验），测试 `test/capability-set.test.ts` 9 条。**测试基线 314 → 323（322 过、0 失败、1 跳过），零回归**。

**⑰ 自己抓出并修掉刚发布的漏洞：`git` 整族退出白名单（D49，实证复现）**：**起因是回头验证 ⑯ 里那句"残留风险"**，结果发现问题**比我自己写的严重得多**。**实测复现**：建真实仓库 → 在其**自己的** `.git/config` 设 `core.fsmonitor` 指向一个会写文件的脚本 + `core.untrackedCache true` → 运行 **`git status`** → **脚本被执行、marker 文件被写出**。而 ⑯ 的白名单把 `git status` 判为"只读免问"。**即：一条被本项目判为不必问的命令，执行了仓库自带的任意代码——正是同一轮文档里写明"不可接受"的那一类失败。** 同族还有 `core.pager`（`git log`）与 `diff.*.textconv`（`git diff`），**所以"按子命令收窄"根本无效**：每个只读子命令都读同一份仓库配置，**那张 `GIT_READ_SUBCOMMANDS` 表没有缩小风险，只是让它看起来被管理了**。**核实无环境变量缓解**：`GIT_CONFIG_NOSYSTEM` 只抑制系统级配置，**关不掉仓库自己的**。**不采用逐键 `git -c` 覆盖**：那要枚举 `fsmonitor`/`pager`/`editor`/`sshCommand`/`hooksPath`/`textconv`/`filter.*`/`alias.*`…——**正是本项目已经栽过两次的"枚举危险项"形态**（argv 方案、字符串检测方案），**同一条错误不犯第三次**。**改用一条准入准则**替代"看起来像只读"：**工具能进白名单，当且仅当它自己的标志、和它读取的任何项目本地配置，都不能让它去执行另一个程序**；据此移出 `git`（已实证）、`rg`（`--pre` 执行外部命令，**本机未装无法核实**）、`npm ls`（读项目 `.npmrc`，**未验证**）。**代价如实说**：`git status` 现在每次都要批准，**这是本轮唯一的用户可见退步**；恢复要等 D26。**验证升级为走完整链路**（runtime→工具→审批门，**不是只查 `decide()`**，因为 D46 已证明"决策对了但没接到工具"是真实故障形态），**并带反证**：先在 `full-access` 下断言投毒仓库**真的执行了**，否则测试可能因 git 缺失或 payload 未触发而空过；再断言中间档下 marker **不出现**。**全量 520 通过 / 0 失败 / 1 跳过。** **最该记的教训不是漏洞本身**：**我用"残留风险"这个措辞描述了一条已经免问放行、已经可被利用的路径**——写下"有风险但先这样"时，若那条路径已在放行，它不是残留风险，是**已发布的漏洞**；**措辞的宽松掩盖了严重性**，与 D26 那次"不做全局开关"的措辞纠正同类。
