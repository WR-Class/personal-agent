**权限架构的关键修正（D22/D23/D24，本批无代码）**：用户反馈"全都要弹窗很麻烦、但边界必须有"，并指出我提的"只读白名单"形态不对。调研了**本项目正在运行的 DSH 自身**（四个权限包的 README，直接从 `app.asar` 读取）、**gemini-cli**（策略引擎源码，深度）、**codex**（审批+沙箱源码，深度）、**crush** 与 **claude-code**（类型定义/源码）。三批结论递进：

1. **D22 根因**：我把"沙箱"和"审批"当成一个机制。它们是两个正交旋钮，且对用户应呈现为**具名档位**（`custom` 可见但不可选）。
2. **D23 内核**：实现应采用**单一优先级规则表 + tier 前缀**（Admin > User > Workspace > Extension > Default **不可倒置**，`priority` 上限 999 防 tier 溢出）。这样"降低打扰"的每一项功能都只是又一条规则，**结构上只能"胜过"某条规则、无法绕开排序**——比"两套机制各自守规矩"更有保证力。
3. **D24 修正重心（最重要）**：**Codex 的降打扰靠沙箱，不靠审批**——受限沙箱下普通命令**静默放行**，审批只是窄的例外通道。**而 Windows 恰是边界最弱的平台**：上游原版 Windows **没有沙箱**，其非升权后端**只能约束写**（读不受限），且**在没有边界时反而强制弹窗**补偿。因此在 Windows 上"审批"不可能成为主要边界。**本项目的诚实定位**：边界 = 路径收敛 + 写预算 + `WritableRoot` 式只读保护 + 子进程环境白名单 + 有界输出 + 审计 + 窄化授权，**而不是隔离**；SAFETY 必须**逐条列出这些不是隔离**。

4. **D25 第三条轴（最重要的一条修正）**：**降打扰不能只靠"调沙箱/调审批"，还要靠"让能力不存在"**——四个独立项目收敛于此（Letta `--tools ""` 原文"把工具从上下文里整个移除"、OpenClaw 只读会话不提供写工具、TrustClaw 按缺席拒绝、nanobot 越界路径不可达）。**疲劳 ∝ 决策数 ∝ 动作空间大小**，所以**缩小动作空间是唯一结构性的降打扰手段**，而不是让提示更聪明。**这修正了 D24 的结论**（D24 说"无沙箱⇒审批为主"，方向对但不完整）。另外两项独立证据：**goose 发布过 macOS 沙箱又把沙箱删了**（原文"has been removed … **not** sandboxed at the OS level"，转回 `GOOSE_MODE` 审批档——已在源码逐字核对，说明**持久价值在逻辑层而非隔离层**）；**qwen-code 让"总是允许"无法击穿自己的分类器**（危险 allow 规则被暂存而非安装，已在源码逐字核对）。

**本批落地顺序（三轴替代两轴，全部无需 shell、可立即实现并测试）**：①**能力存在性**（会话级工具集合——缺席即无需审批）＋**仓库外记忆化**＋**各轴独立** → ②**授权绑定内容哈希 + 执行前复验 + 漂移即拒**（与已有写入账本"执行前算账"同构）→ ③规则表内核（D23）→ ④影子快照/选择性还原（**可部分弥补"无沙箱＝无回滚"，候选**）→ ⑤命令执行。

**② 授权绑定内容哈希已完成（本片，已测）**：读代码后发现**授权缓存早就存在**，所以本片不是"新增缓存"而是**"修缓存键错了"**。旧实现用字符串比对（`grant.argumentsJson === JSON.stringify(args)`）——**字符串相等 ≠ 同一个动作**。**已实测**：`{"path":"a.txt","content":"x"}` 与 `{"content":"x","path":"a.txt"}` **键序不同即不匹配** ⇒ 同一动作**再次弹窗**（现状能工作只因模型逐字节重复自己，那是运气不是性质）。改为 `actionBinding = sha256(canonicalize({tool, args}))`，**直接复用 `gene.ts` 既有的 `canonicalize`**（全库只有一份稳定序列化）；**工具名进哈希**，一条工具的授权永不满足另一条。另修一处我自己引入的健壮性缺口：`JSON.parse` 对畸形 grant 会抛，原样会**崩掉整个工具调用**，改为**失败即视为不匹配**（畸形 grant 什么都不授权，但不拖垮调用）。测试 8 条（键序、嵌套键序、值变化、跨工具隔离、文本拼写、`undefined` 键、**数组顺序须区分**、地址格式）。**测试基线 323 → 331（330 过、0 失败、1 跳过），零回归**。**诚实的边界**：本绑定**只含动作参数**，不含 cwd、不含环境哈希、不含被操作文件当前内容，因此**不等于 OpenClaw 的完整绑定**——本片解决"同一动作被反复问"，**尚未**解决"批准之后世界变了"（下一片与本项目既有的执行前复算 `sameFile` 合并处理）。

**② 批准后漂移即拒已完成（本片，已测）**：发现**真实缺陷**——`edit_file` 在**批准之前**读一次内容，此后**再也不读**；批准与写入之间的窗口**不是瞬时的**（TTL 就有 2 分钟），所以文件被换掉后，**用陈旧读取算出的内容照样写回**（**静默丢失更新**）。`patch_file` **更严重**：新内容由 `newText` **拼接进那次陈旧读取**得到，并发编辑**不只是被覆盖，而是被悄悄回退**。既有的 `sameFile` **不够**——它只校验**路径**仍解析到同一处，**完全不看内容**。**先写失败测试证明缺陷可复现**（在 `approve` 回调里改写文件，修前两条全红），再改代码。做法：`contentStamp`＝sha256 + `unchangedSinceApproval(再读一次并比对)`，文件消失或不可读**也算漂移**。**覆盖范围按"操作者究竟批准了什么"逐个判断**：edit/patch 批准内容 ⇒ 校验；delete **预览了内容** ⇒ 也校验（否则删掉操作者**从未看过**的东西）；create **本来就安全**（`flag:"wx"` 由**操作系统原子拒绝**，原生机制强于自写检查）；rename **刻意不加**（其提示不展示内容，批准的是路径；目标被占用这一真实漂移已由 `sameFile` 覆盖）。**过程中犯了同形的错并自查出来**：delete 第一版把指纹写在**批准之后**，等于**拿内容和它自己比**、永远相等、检查形同虚设——**被自己新加的测试当场抓住**，改为预览与指纹来自同一次读取。测试 6 条。**测试基线 331 → 337（336 过、0 失败、1 跳过），零回归**。**实质**：把绑定从"批准过这个**动作**"推进到"批准过这个**内容**"。**仍未做**：绑定**尚不含 cwd 与环境哈希**；且**检查是 TOCTOU 窗口收窄、不是消除**——校验与 `rename` 之间仍有极短窗口，无沙箱无文件锁，**不宣称原子性**。

**③ 规则表内核已完成（本片，已测）**：单一优先级规则表取代写死的判定，机制**照 D23 记录实现**：`tool`（含 `*`）/`decision`/`tier`/`priority`/可选 `when(args)`/`reason`，**有效优先级 = `tier + clamp(priority,0,999)/1000`**，**排序一次、首个匹配者胜出**，**无匹配即 deny**，**谓词抛异常即不匹配**（fail-closed）。**最要紧的不变量**：`tier` 前缀（`DEFAULT<EXTENSION<WORKSPACE<USER<ADMIN`）**不可被 priority 倒置**，`priority` 上限 999 正是为此——已对**每一对相邻 tier** 测试"下层最高 < 上层最低"。**读代码后收敛了范围（重要）**：我此前把四条轴并列待统一，但**它们性质不同，硬凑一张表是假对称**——路径收敛是**不变量**、写预算是**计数器**、能力集合是**会话属性（运行在表之前）**，**只有 allow/approve/deny 才是"决策"**；其余三者**刻意留在表外**，因为**建模成规则就会让高优先级规则放宽它们**。**行为不变是硬要求**：`DEFAULT_RULES` **逐字复现**原 switch，所以**换机制不等于换行为**（既有 337 条全绿为证）；差别是**行为从代码变成数据**——可检查、可按 `id` 归因、可被更高 tier 覆盖而不改文件。测试 14 条（行为保真、tier 不可倒置、失败即关闭）。**测试基线 337 → 351（350 过、0 失败、1 跳过），零回归**。**仍未做**：**尚未引入任何具名档位**（顺序刻意：**档位名必须在其能表达的语义已存在之后才定**）；**规则表尚未接配置**（只有内置规则，故 D26 的"仓库配置不得自行提权"目前无攻击面，但接配置时必须同时落地）；**审计尚未记录 `rule.id`**（`decide()` 已返回，调用点只用 `.decision`，归因能力已具备但未接上）。

**③ 剩余部分已完成：归因接上 + 具名档位（本片，已测）**。**归因**：`AuditEvent` 新增**可选** `rule?: string | null`，拒绝时写入**做出该决定的规则 id**——`null`（表做了决定但无规则匹配）与**字段缺失**（旧行）**语义不同**，已分别用测试钉住；审计校验器**逐字段重建**记录，故**类型/写入/校验器三处同时改**（只加字段会被静默丢弃）。**审计仍只记拒绝、不新增 allow 通道**——读类工具刻意零确认，记录每次 allow 纯属噪声。**一处既有测试据此更新**（它断言了原写死的拒绝文案），属**有意的可解释性改进**：拒绝现在**能说出是哪条规则**。**具名档位**（`src/tiers.ts`）：`read-only`／`workspace-write`（默认）／`full-access`，每档显式给出**工具集合（缺席而非拒绝）＋规则表**；**两条约束在代码里强制**：**(1)** 档位**无法放宽不变量**（路径收敛与能力集合不是规则，故本模块只能选权限决策，有测试断言）；**(2)** **宽松档必须显式记录**——`resolveTier` 对未知名字**报错而不回落**（回落到宽松档＝**因错别字发放全权**）。**写代码时被自己的测试抓到一个真实逻辑错误**：`read-only` 第一版把通配 `deny`(900) 排在 `read_file` 的 `allow`(500) **之上**，**通配拒绝把读也吞掉**——该档实际变成"什么都不读"。**排序就是机制，那两个数字是承重的**；已改为 allow 900 > deny 800 并注明原因。测试 14 条。**测试基线 351 → 365（364 过、0 失败、1 跳过），零回归**。**仍未做**：**档位尚未接到 CLI**（`cli.ts` 仍用全集与内置规则，**用户暂时看不到行为变化**），接线时须同时落地"移除边界必须落盘可审计"与"仓库自带配置不得自行提权"；`full-access` **只是"不再问"，不是"没有边界"**（路径收敛/写预算/漂移检测/审计照常生效）；**档位名是设计产物，用户可能想改**（改名只动 `tiers.ts`）。

**④ 队列校正（D33，无代码）**：我上一条建议"下一片做规则表内核"是**过期的**——核实后发现 `rule-table.ts`（D31）与 `tiers.ts`（D32）**已完成并接线**（`cli.ts:254-269` 按档位工具列表构造 `ToolRegistry` 与规则表），测试基线 **365（364 过 / 0 失败 / 1 跳过）**。**剩余队列的真实状态**：`SWARM_LOOP` §8 的 5 项里，**1、2、5 全部等 M3 受控进程工具**（`src/` 下**不存在** shell/exec 模块，已核实），**3 明确以 ①② 为前置**，**4 是等 outcome 数据积累而非可实现项**。所以**剩余队列不是可逐条执行的清单，而是被同一个尚未构建的能力卡住**。**M3 是改变产品性质的决策，不是排期问题**：今天全部边界（路径收敛／写预算／能力存在性／授权绑定／漂移检测）**都只作用于文件工具**，而**命令执行不受这些约束**（D27 已实测）；故须**同时**决定命令的能力存在性、授权绑定（按 D29/D30）、写账本是否/如何覆盖命令副作用（**诚实的困难**：`rm -rf` 无法像文件工具那样精确计文件数），以及**在无沙箱前提下能否接受命令执行**（Codex 在同样平台上选择强制弹窗补偿，D24）。**不依赖 M3 仍可做的方向**：④影子快照/选择性还原、规则表接配置（须同时落地"移除边界落盘可审计"与"仓库配置不得自行提权"）、`--tier` 端到端验证。

**⑤ 附加可读根已完成（D35，本片，已测）**：核实出**路径轴此前只有"收紧"一个方向**——`extraRoots` 进的是 deny 列表、`PERSONAL_AGENT_PROTECTED_ROOTS` 只增不减，所以**连 `read_file` 都出不了工作区**。这正是用户说的"审计别人的代码/看工作区外的二进制"做不了的真实原因（**不只是没 shell**）。现已加入**只读**附加根：`--trust-root <dir>` / `--untrust-root` / `--trusted`，信任存 **agent home 的 `trust.json`（不在工作区**，克隆恶意仓库无法自带授权，照 grok-cli），**每一步重读不缓存**（照 qwen-code），**授予与撤销都写审计**。**读写分离用两个函数而非一个布尔参数**（布尔量会在重构中被误翻而无人察觉），测试**专门断言三个写工具在授予后仍以 `path escapes the workspace` 拒绝**。**开发中被自己抓到三个错误**：① 首版 helper 在放行后又委托回严格检查，**附加根永远不可达**；② 修正后**过度套用** `protectedRoots()`（含 `%LOCALAPPDATA%` 整棵宿主树），导致"授予的目录仍被拒为 sensitive"；③ 测试用 `as const` 元组传参致工具收到空 `path`，**失败暴露的是测试自身**。**诚实边界**：**放宽可读根＝给的是整棵目录树，不是"只读那几个文件"**（`sensitivePathName` 挡 `~/.ssh/id_rsa`，挡不住名如常物的敏感文件），CLI 授予时已明说。测试 13 条；CLI 真机验证 grant→list→revoke→list 与审计两条全通；**基线 365 → 378（377 过 / 0 失败 / 1 跳过），零回归**。**仍未做**：`read_file` 仍是 UTF-8（**读二进制缺一步**，用户已确认逆向两个方向都可能）；**无 shell**（(a)-(d) 四问未定夺，见 D34）。

**明确拒绝的共享反模式**：**"因为有沙箱/Docker/云兜住，所以可以宽松"**——OpenClaw 默认沙箱关闭且不提示、Hope Agent 与 AutoGen 依赖 Docker、TrustClaw 外包到云、Letta 让 agent 改写自己的 harness；**这些安全叙事全部依赖本项目刻意不具备的隔离**。本项目约束更严，姿态必须更严。

**术语与措辞纠正（D26，用户追问后修订）**：**(a) 第二自报通道**＝"另一个模型说这轮成功/批准"——它和"干活的模型自报成功"**结构上是同一个东西**，都不得采信；系统可信来源**只有机械事实**。这是 D14/D15/D19 拒绝模型评审者的共同依据（D19 尤其：参考实现里评审者的准确率是拿"最终是否真的整合成功"回头校准的，而本项目**尚无验证执行器**，所以模型评审者会是**一个永远无法知道准不准的裁判**）。**(b) 措辞纠正**：我先前写"不做纯全局 yolo 开关"**不准确**——事实是 **DSH／Codex／claude-code／gemini-cli／crush 全都提供全权模式**，这本身不是缺陷。准确的规则是：**不是"不做全局开关"，而是"不做只有全局开关"**（多档位 + 安全默认档）；**移除边界必须是落盘可审计的决定**（"你做了这个决定"），**不是凭权限标签即可解锁**（OpenClaw `full` 仅凭 `operator.admin`）；**仓库自带配置不得自行提权**（claude-code 拒绝仓库内 `settings.json` 设 `bypassPermissions`）。**(c)** 不采用 Windows 受限令牌方案的理由**不是做不到，而是交易不好**：上游自认只能约束写（读不受限、网络挡不住），完整版要在用户机器上**建本地账户 + 装特权服务 + 改防火墙**，对开源个人零依赖产品代价不成比例。

**已验证而非假设**：本项目**已有真实的子进程环境白名单**（`tool-environment.ts` 只放行 PATH/SystemRoot/Windir/ComSpec/Pathext，`tools.ts` 拒绝回落 `process.env`），所以 Codex 那个"默认把密钥透传给子进程"的坑**在本项目不存在**。另外核查发现：**`isReadOnly` 在 gemini-cli 里不门控执行**（其注释写明用途是并行安全），plan 的只读边界完全由规则表强制；**`claude-code` 目录是文档/SDK 仓库而非源码检出**（无应用源码），其信任对话框与"总是允许"写入路径**属"文档提及"而非"代码可验证"**；`extra\cursor`/`extra\trae` 是专有存根（3/2 个文件），**不可作为源码依据**；`crush` 的许可证是 **FSL-1.1-MIT**，非标准 OSI 许可。

**本轮工具限制（如实记录）**：**`web_search` 在本会话不可用**（缺 `DEEPSEEK_API_KEY`）；因此外部项目调研改用 `web_fetch` 直连 GitHub REST API，**每个项目都以 HTTP 200 + 至少一份一手来源验证**（含真实 star 数、许可证、`pushed_at`），**未经验证的条目单列且不当作事实**（如 `Doriandarko/agent-zero` 返回 404，已排除）。7. **结构化验证声明 + 轮末比对已完成**：`Gene.validation` 从"提示词里的一行字"变成结构化声明（`files-written`/`no-write`/`tool-used`/`command`），`mintGene` 仍接受裸字符串并归一化为 `command`；轮末按日志事实**逐条比对**，三态 `met`/`unmet`/`unverifiable`——**`unverifiable` 是独立结果，既不算 met（那是伪造证据）也不算 unmet（那是惩罚可能确实做了的工作）**；`files-written` 按集合相等双向比对（少报也算 unmet）；被推翻的声明把本轮降为 `partial`，结果写进周期证据与 outcome 行。**能抓"过度声明"，不能证"测试通过"**——`command` 在无 shell 时一律 `unverifiable` 并明写原因。顺带修一个真缺陷：`--mint-gene` 曾被 UTF-8 BOM 卡死并误报"不是合法 JSON"（Windows 编辑器默认写 BOM）。证据见 D20。
