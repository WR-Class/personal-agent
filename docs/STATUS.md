**权限架构的关键修正（D22/D23/D24，本批无代码）**：用户反馈"全都要弹窗很麻烦、但边界必须有"，并指出我提的"只读白名单"形态不对。调研了**本项目正在运行的 DSH 自身**（四个权限包的 README，直接从 `app.asar` 读取）、**gemini-cli**（策略引擎源码，深度）、**codex**（审批+沙箱源码，深度）、**crush** 与 **claude-code**（类型定义/源码）。三批结论递进：

1. **D22 根因**：我把"沙箱"和"审批"当成一个机制。它们是两个正交旋钮，且对用户应呈现为**具名档位**（`custom` 可见但不可选）。
2. **D23 内核**：实现应采用**单一优先级规则表 + tier 前缀**（Admin > User > Workspace > Extension > Default **不可倒置**，`priority` 上限 999 防 tier 溢出）。这样"降低打扰"的每一项功能都只是又一条规则，**结构上只能"胜过"某条规则、无法绕开排序**——比"两套机制各自守规矩"更有保证力。
3. **D24 修正重心（最重要）**：**Codex 的降打扰靠沙箱，不靠审批**——受限沙箱下普通命令**静默放行**，审批只是窄的例外通道。**而 Windows 恰是边界最弱的平台**：上游原版 Windows **没有沙箱**，其非升权后端**只能约束写**（读不受限），且**在没有边界时反而强制弹窗**补偿。因此在 Windows 上"审批"不可能成为主要边界。**本项目的诚实定位**：边界 = 路径收敛 + 写预算 + `WritableRoot` 式只读保护 + 子进程环境白名单 + 有界输出 + 审计 + 窄化授权，**而不是隔离**；SAFETY 必须**逐条列出这些不是隔离**。

4. **D25 第三条轴（最重要的一条修正）**：**降打扰不能只靠"调沙箱/调审批"，还要靠"让能力不存在"**——四个独立项目收敛于此（Letta `--tools ""` 原文"把工具从上下文里整个移除"、OpenClaw 只读会话不提供写工具、TrustClaw 按缺席拒绝、nanobot 越界路径不可达）。**疲劳 ∝ 决策数 ∝ 动作空间大小**，所以**缩小动作空间是唯一结构性的降打扰手段**，而不是让提示更聪明。**这修正了 D24 的结论**（D24 说"无沙箱⇒审批为主"，方向对但不完整）。另外两项独立证据：**goose 发布过 macOS 沙箱又把沙箱删了**（原文"has been removed … **not** sandboxed at the OS level"，转回 `GOOSE_MODE` 审批档——已在源码逐字核对，说明**持久价值在逻辑层而非隔离层**）；**qwen-code 让"总是允许"无法击穿自己的分类器**（危险 allow 规则被暂存而非安装，已在源码逐字核对）。

**本批落地顺序（三轴替代两轴，全部无需 shell、可立即实现并测试）**：①**能力存在性**（会话级工具集合——缺席即无需审批）＋**仓库外记忆化**＋**各轴独立** → ②**授权绑定内容哈希 + 执行前复验 + 漂移即拒**（与已有写入账本"执行前算账"同构）→ ③规则表内核（D23）→ ④影子快照/选择性还原（**可部分弥补"无沙箱＝无回滚"，候选**）→ ⑤命令执行。

**① 能力存在性已完成（本片，已测）**：`ToolRegistry` 增加可选 `available` 集合与 `has()`；**缺席在两个方向同时强制**——`definitions()` 不向模型暴露该工具，`execute()` 按名字拒绝。**只从提示词里藏起来、却仍能被调用，那是"伪装成缺席的拒绝"**，而这个边界之所以廉价，正因为它**只在两处一致时才成立**。拒绝文案刻意与普通失败区分：**"this tool is not available in this session; it is a policy boundary, not a transient failure"**——让模型知道这是本会话的**常驻属性**，不要重试或找绕路（依据：nanobot 的边界错误文案、opencode 的 `CorrectedError` 把原因回给模型）。改动仅 `src/tools.ts`（`available` + `has()` + `definitions()` 过滤 + `execute()` 前置拒绝 + 未注册项校验），测试 `test/capability-set.test.ts` 9 条。**测试基线 314 → 323（322 过、0 失败、1 跳过），零回归**。

**⑰ 自己抓出并修掉刚发布的漏洞：`git` 整族退出白名单（D49，实证复现）**：**起因是回头验证 ⑯ 里那句"残留风险"**，结果发现问题**比我自己写的严重得多**。**实测复现**：建真实仓库 → 在其**自己的** `.git/config` 设 `core.fsmonitor` 指向一个会写文件的脚本 + `core.untrackedCache true` → 运行 **`git status`** → **脚本被执行、marker 文件被写出**。而 ⑯ 的白名单把 `git status` 判为"只读免问"。**即：一条被本项目判为不必问的命令，执行了仓库自带的任意代码——正是同一轮文档里写明"不可接受"的那一类失败。** 同族还有 `core.pager`（`git log`）与 `diff.*.textconv`（`git diff`），**所以"按子命令收窄"根本无效**：每个只读子命令都读同一份仓库配置，**那张 `GIT_READ_SUBCOMMANDS` 表没有缩小风险，只是让它看起来被管理了**。**核实无环境变量缓解**：`GIT_CONFIG_NOSYSTEM` 只抑制系统级配置，**关不掉仓库自己的**。**不采用逐键 `git -c` 覆盖**：那要枚举 `fsmonitor`/`pager`/`editor`/`sshCommand`/`hooksPath`/`textconv`/`filter.*`/`alias.*`…——**正是本项目已经栽过两次的"枚举危险项"形态**（argv 方案、字符串检测方案），**同一条错误不犯第三次**。**改用一条准入准则**替代"看起来像只读"：**工具能进白名单，当且仅当它自己的标志、和它读取的任何项目本地配置，都不能让它去执行另一个程序**；据此移出 `git`（已实证）、`rg`（`--pre` 执行外部命令，**本机未装无法核实**）、`npm ls`（读项目 `.npmrc`，**未验证**）。**代价如实说**：`git status` 现在每次都要批准，**这是本轮唯一的用户可见退步**；恢复要等 D26。**验证升级为走完整链路**（runtime→工具→审批门，**不是只查 `decide()`**，因为 D46 已证明"决策对了但没接到工具"是真实故障形态），**并带反证**：先在 `full-access` 下断言投毒仓库**真的执行了**，否则测试可能因 git 缺失或 payload 未触发而空过；再断言中间档下 marker **不出现**。**全量 520 通过 / 0 失败 / 1 跳过。** **最该记的教训不是漏洞本身**：**我用"残留风险"这个措辞描述了一条已经免问放行、已经可被利用的路径**——写下"有风险但先这样"时，若那条路径已在放行，它不是残留风险，是**已发布的漏洞**；**措辞的宽松掩盖了严重性**，与 D26 那次"不做全局开关"的措辞纠正同类。

**必须逐调用、按原顺序、带原索引重放整个计费循环**。**⇒ (C) 不是"读一遍日志"，是"把计费规则写第二遍"，而第二份实现就是"一个问题两个答案"、分歧不报错；更糟的是规则变更后旧日志会重算出不同的历史，派生值跨版本静默改变含义 —— 这比存一份副本更坏**（副本至少冻结了当时的判断）。**外部取证（本地 `_research/repos` 源码直读；⚠️ 派出的子代理在收尾前失败且无输出，外部部分改为自己做，只覆盖两个产品）**：**Codex** 的 `update_plan` 是 `PlanItemArg { step: String, status: StepStatus }`、`StepStatus = Pending|InProgress|Completed`、`plan: Vec<PlanItemArg>`（**整份而非增量**），**纯模型自报、无 claim 无证据无校验**，而 handler 的全部逻辑就是 `session.send_event(turn, EventMsg::PlanUpdate(args))` 然后返回**空的** tool output（`code_mode_result` 是空对象）；**opencode** 把 todo 存在 **SQL 表** `TodoTable`，`update` 在**一个事务里先整份删除再整份插入**（`tx.delete(TodoTable).where(eq(TodoTable.session_id, …))` → `tx.insert(…)`），`status` 同样模型自报。⇒ **两个产品、两种截然不同的存储机制（发事件 vs SQL 事务整份替换），语义完全相同：整份替换、latest-wins、模型自报、没有任何跨轮累积逻辑** ⇒ **业界不累积，业界替换**；而它负担得起"替换"是因为**它信任模型写的 `completed`，状态由模型自己一轮轮带下去**。⇒ **本产品的处境因此被精确定位：`task-state` 已经是业界那个形状（整份 latest-wins、存会话日志、模型重写步骤文本），唯一差别是本项目拒绝让模型写 `done`（D14/D15/D26）⇒ 缺口不是"少了累积机制"，而是"业界用信任模型填的那个洞，本项目必须用别的东西填"，这个缺口是那条拒绝的直接代价、不是设计疏忽**。**⚠️ 本轮最重要的发现：累积不是 claim-kind 无关的** —— `tool-used` 是**下界**（D61 已核实），**并集成立且自然**；**`files-written` 是双向集合相等**（`const actual = [...new Set(evidence.filesWritten)].sort()` 后与 paths 比，D61 据此判定 `paths` 不可变），**⚠️ 并集不成立**：claim `files-written:[a.ts]` 的意思是"**恰好**写了这些"，**对各轮取并集后任何一轮多写任何文件都会让原本 `met` 的 claim 变成 `unmet`，即累积反而让已达成的步骤失效**；`no-write` 跨轮会变成"任何一轮都没写过"，**讲得通但不再是同一个命题**；`command` 恒 `unverifiable` 故无关。**⇒ 对 `files-written` 可能根本不存在可靠的累积规则**：它天然是每轮命题，拉到跨轮就改变了含义 —— **这与 D61 的 `paths` 不可变同根（双向集合相等），也是 D64"任务判定不得给本轮降级"那个不对称性的第三面**。**⇒ 任何累积方案都必须逐 kind 定义，且很可能要公开声明一条新能力上限：以 `files-written` 为验收条件的步骤，其达成只在当轮可判、跨轮不可累积**，与"`command` 恒判不了"并列。**给操作员的裁决材料**：**(A) 已死**不必再考虑；**存在一个"半份 (C)"是最小可行形状** —— 只累积 `tools`（可从日志直接收集，不需重放计费循环）、不累积 `filesWritten`，代价是 `files-written` 步骤永远只能当轮判，**而这恰好与上面的结论一致（它本来就不该累积）**；**(D) 存每轮证据、累积=并集、按需重判**是完整解（**存事实不存结论** ⇒ 语义变更时重判自动跟随；**"哪一轮的 met 算数"被消解**，对并集重跑同一个 `assessTaskState` 即可；按 §4.3 判据删掉它丢的是真相 ⇒ **是新事实而非派生视图，允许存在会话日志之外**；每轮一条、不可变、单调 ⇒ **后续轮次不可能与之矛盾**），但要求每轮多写一条事件且须先定并集语义；**(B) 不建议**（两个可变快照正是 ADR-0001 要防的形状）；**业界做法本项目用不了**（靠信任模型自报，而那是有意拒绝的通道）。**未取证/未验**：goose（`crates/goose/src/agents/platform_extensions/todo.rs`）、aider、gemini-cli（`packages/core/src/utils/planUtils.ts`）、crush（`internal/agent/tools/todos.go`）、**opencode 的 v2 session core**（其 `AGENTS.md` 提到 durable `session_input` 行、投影与 "Context Epoch persistence"，**可能有更接近 event sourcing 的做法，未读**）、LangGraph checkpointer、Temporal event history、**宿主 dsh 的 swarm 记录方式（本环境读不到该路径）**；**"业界不累积"只由两个产品支撑，样本偏小，不应据此推广**。

**明确拒绝的共享反模式**：**"因为有沙箱/Docker/云兜住，所以可以宽松"**——OpenClaw 默认沙箱关闭且不提示、Hope Agent 与 AutoGen 依赖 Docker、TrustClaw 外包到云、Letta 让 agent 改写自己的 harness；**这些安全叙事全部依赖本项目刻意不具备的隔离**。本项目约束更严，姿态必须更严。

**术语与措辞纠正（D26，用户追问后修订）**：**(a) 第二自报通道**＝"另一个模型说这轮成功/批准"——它和"干活的模型自报成功"**结构上是同一个东西**，都不得采信；系统可信来源**只有机械事实**。这是 D14/D15/D19 拒绝模型评审者的共同依据（D19 尤其：参考实现里评审者的准确率是拿"最终是否真的整合成功"回头校准的，而本项目**尚无验证执行器**，所以模型评审者会是**一个永远无法知道准不准的裁判**）。**(b) 措辞纠正**：我先前写"不做纯全局 yolo 开关"**不准确**——事实是 **DSH／Codex／claude-code／gemini-cli／crush 全都提供全权模式**，这本身不是缺陷。准确的规则是：**不是"不做全局开关"，而是"不做只有全局开关"**（多档位 + 安全默认档）；**移除边界必须是落盘可审计的决定**（"你做了这个决定"），**不是凭权限标签即可解锁**（OpenClaw `full` 仅凭 `operator.admin`）；**仓库自带配置不得自行提权**（claude-code 拒绝仓库内 `settings.json` 设 `bypassPermissions`）。**(c)** 不采用 Windows 受限令牌方案的理由**不是做不到，而是交易不好**：上游自认只能约束写（读不受限、网络挡不住），完整版要在用户机器上**建本地账户 + 装特权服务 + 改防火墙**，对开源个人零依赖产品代价不成比例。

**已验证而非假设**：本项目**已有真实的子进程环境白名单**（`tool-environment.ts` 只放行 PATH/SystemRoot/Windir/ComSpec/Pathext，`tools.ts` 拒绝回落 `process.env`），所以 Codex 那个"默认把密钥透传给子进程"的坑**在本项目不存在**。另外核查发现：**`isReadOnly` 在 gemini-cli 里不门控执行**（其注释写明用途是并行安全），plan 的只读边界完全由规则表强制；**`claude-code` 目录是文档/SDK 仓库而非源码检出**（无应用源码），其信任对话框与"总是允许"写入路径**属"文档提及"而非"代码可验证"**；`extra\cursor`/`extra\trae` 是专有存根（3/2 个文件），**不可作为源码依据**；`crush` 的许可证是 **FSL-1.1-MIT**，非标准 OSI 许可。

**本轮工具限制（如实记录）**：**`web_search` 在本会话不可用**（缺 `DEEPSEEK_API_KEY`）；因此外部项目调研改用 `web_fetch` 直连 GitHub REST API，**每个项目都以 HTTP 200 + 至少一份一手来源验证**（含真实 star 数、许可证、`pushed_at`），**未经验证的条目单列且不当作事实**（如 `Doriandarko/agent-zero` 返回 404，已排除）。7. **结构化验证声明 + 轮末比对已完成**：`Gene.validation` 从"提示词里的一行字"变成结构化声明（`files-written`/`no-write`/`tool-used`/`command`），`mintGene` 仍接受裸字符串并归一化为 `command`；轮末按日志事实**逐条比对**，三态 `met`/`unmet`/`unverifiable`——**`unverifiable` 是独立结果，既不算 met（那是伪造证据）也不算 unmet（那是惩罚可能确实做了的工作）**；`files-written` 按集合相等双向比对（少报也算 unmet）；被推翻的声明把本轮降为 `partial`，结果写进周期证据与 outcome 行。**能抓"过度声明"，不能证"测试通过"**——`command` 在无 shell 时一律 `unverifiable` 并明写原因。顺带修一个真缺陷：`--mint-gene` 曾被 UTF-8 BOM 卡死并误报"不是合法 JSON"（Windows 编辑器默认写 BOM）。证据见 D20。
